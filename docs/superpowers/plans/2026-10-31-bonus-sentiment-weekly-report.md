# Bonus Twist — Sentiment Tracking & the Automatic Weekly Insights Report

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The README's bonus twist becomes literally true: every completed week produces a persisted
insights report (sentiment index, trend, and recurring complaints ranked with week-over-week deltas)
without anyone clicking, and the dashboard shows the report plus the sentiment trend it is built from.

**Architecture:** One pure module (`weekly-report.ts`) computes a week-aligned report and a rolling
sentiment tracker from ticket rows. One store module (`weekly-report-store.ts`) owns persistence
behind a five-function interface, so the rules are unit-tested with a fake and Prisma is a thin
adapter. `GET /api/businesses/[id]/insights` lazily materialises the missing completed-week report, so
the feature works with no scheduler; `GET|POST /api/cron/weekly-insights` does the same sweep for every
business on a weekly schedule (`vercel.json`), both idempotent on `(businessId, weekStart)`.

**Tech Stack:** Next.js 16 App Router, React 19, TypeScript (strict + `exactOptionalPropertyTypes`),
Prisma 6 + Postgres, `node:test`, `node --experimental-strip-types`.

**Spec:** `docs/prd/ps_2_5_master_executable_prd_team_41.md` rev 4 — §1.1 (bonus twist), §1.3
(`/dashboard?tab=brain` shows "Sentiment Tracker & Automated Weekly Recurring Complaints Report"),
§3 (Ticket.sentiment enum), §6 Phase 3 checklist line "Implement weekly sentiment & recurring
complaints aggregator". README line 12 states the bonus twist verbatim.

## Global Constraints

- Frozen contracts: existing `InsightsResponse` fields and the Phase 3 gate's insights assertions stay
  valid; new response fields are additive.
- `businessId` always comes from the authenticated session or a verified cron secret — never from a
  request body.
- No secret in the client bundle. `CRON_SECRET` unset ⇒ cron route `503`, exactly like email poll.
- Weeks are ISO weeks in **UTC**: Monday `00:00:00Z` inclusive → next Monday exclusive. A "completed
  week" is the previous Monday–Sunday window.
- A completed week's report is written once and never regenerated by normal traffic (idempotent on
  `(businessId, weekStart)`); a re-run must not duplicate the row or move `generatedAt`.
- Pure code is deterministic and returns new objects (no mutation of input rows).
- Commit style: Conventional Commits, no attribution trailer.
- `npm test` stays green; every new pure function has a `node:test` case; the gate is executable proof.

## Rulings

- **Weekly report is delivered in-dashboard + API + persisted archive, not emailed.** `escalationEmail`
  exists, but the only mail transport in this repo is the owner's connected Gmail
  (`sendEmailForBusiness` requires `EMAIL_NOT_CONNECTED` to be false). Sending a "weekly report" email
  from the judge's own mailbox would be a fabricated delivery, so it is out of scope. Cost if wrong:
  one follow-up task once a real transactional mail key exists.
- **The rolling 7-day card stays.** It answers "what is happening now"; the weekly report answers "what
  did the completed week look like". Both are labelled so a judge never confuses the two windows.
- **Recurring = `count >= 2` AND (`negative >= 1` OR `escalated >= 1`).** A repeated all-positive intent
  is not a complaint. Cost if wrong: an owner who wants "top repeated topics" reads the live card.
- **Completed weeks are immutable snapshots.** Late-arriving data outside the window is ignored by
  definition; only the rolling card reflects it.

## Review Focus

1. **Week boundary correctness** — Sunday 23:59 vs Monday 00:00 UTC, cross-year weeks, and `weeksAgo`
   arithmetic must never produce a 6- or 8-day window or a shifted Sunday-start week.
2. **Idempotency of the automatic path** — two simultaneous `GET /insights`, or a cron re-run, must
   leave exactly one row for `(businessId, weekStart)` and must not move `generatedAt`.
3. **Empty and single-ticket weeks** — no division by zero, a zero-ticket week still produces a valid
   report, and a "baseline" trend is not reported as "improving".
4. **Tenant boundary** — an owner can never read another business's weekly report; the cron sweep is
   the only cross-business path and is secret-gated.
5. **Graceful degradation** — if report persistence fails, the insights `GET` still returns the rolling
   report with `weeklyReport: null` rather than 500.
